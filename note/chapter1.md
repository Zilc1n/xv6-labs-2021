
# 操作系统接口：xv6 的核心交互

xv6 操作系统通过一系列强大的**系统调用**，为用户程序提供了与内核交互的接口。理解这些接口是掌握 xv6 运作方式的关键。本章将深入探讨进程、内存、I/O 与文件描述符以及管道等核心概念。

---

## 1. 进程与内存管理

xv6 中的**进程**是程序执行的基本单位。每个进程都拥有独立的**用户空间内存**（包括指令、数据和栈），以及内核维护的私有**进程状态**。xv6 实现了**分时多任务**，透明地在多个等待执行的进程之间切换 CPU，通过保存和恢复进程的 CPU 寄存器来实现。内核使用**进程 ID（PID）**来唯一标识每个进程。

### `fork()`：创建新进程

`fork()` 系统调用允许进程**创建新的子进程**。它会复制父进程的整个内存内容，使子进程成为父进程的精确副本。`fork()` 在父进程和子进程中都会返回一个值：

- **父进程**中，`fork()` 返回**子进程的 PID**。
- **子进程**中，`fork()` 返回 **0**。

考虑以下 C 语言代码片段：

```c
// fork() 在父进程中返回子进程的 PID，在子进程中返回 0。
int pid = fork();
if (pid > 0) {
    printf("parent: child=%d\n", pid);
    pid = wait((int *)0);
    printf("child %d is done\n", pid);
} else if (pid == 0) {
    printf("child: exiting\n");
    exit(0);
} else {
    printf("fork error\n");
}
```

- **`exit()` 系统调用**：导致调用进程终止执行，并释放其占用的所有资源（如内存和打开的文件）。`exit()` 接受一个整数状态参数，通常 `0` 表示成功，非 `0` 表示失败。
- **`wait()` 系统调用**：用于父进程**等待**其某个子进程退出。它返回已退出子进程的 PID，并将子进程的退出状态复制到传入的地址（如果不需要状态，可传入 `0`）。如果调用进程没有子进程，`wait()` 会立即返回 `-1`；如果没有子进程退出但有子进程仍在运行，`wait()` 会阻塞直到有子进程退出。

在上述示例中，输出顺序可能因调度而异，`parent: child=2886` 和 `child: exiting` 可能会以任意顺序出现。子进程退出后，父进程的 `wait()` 调用将返回，接着打印 `child 2886 is done`。

**重要提示：** 尽管子进程最初与父进程共享相同的内存内容，但它们拥有**独立的内存空间和寄存器**。在一个进程中修改变量不会影响另一个进程。例如，`wait()` 的返回值存储在父进程的 `pid` 变量中，不会影响子进程中仍为 `0` 的 `pid` 变量。

### `exec()`：加载并执行新程序

`exec()` 系统调用用于**替换**当前进程的内存映像。它会从文件系统加载一个可执行文件，并用其内容替换调用进程的现有内存。该文件必须采用特定的格式（xv6 使用 **ELF 格式**，将在第三章详细讨论），该格式定义了指令、数据的位置以及程序的入口点。

`exec()` 成功执行后，**不会返回到调用它的进程**；而是从加载文件的新程序入口点开始执行。它接受两个参数：可执行文件的**文件名**和**字符串参数数组**。

例如：

```c
#include "kernel/types.h"
#include "kernel/stat.h"
#include "user/user.h"

int main() {
    char *argv[3];
    argv[0] = "echo";
    argv[1] = "hello";
    argv[2] = 0; // 参数列表以 NULL 结尾

    exec("echo", argv); // 尝试执行 echo 程序
    printf("exec error\n"); // 如果 exec 失败，才会执行到这里

    exit(0);
}
```

这段代码会用 `echo` 程序替换当前运行的程序，参数列表为 `echo hello`。大多数程序会忽略参数数组中的第一个元素，它通常是程序本身的名称。

xv6 的 shell 利用 `fork()` 和 `exec()` 来为用户运行程序。其主要结构非常简洁：shell 从用户输入读取一行命令，`fork()` 创建一个子进程，父进程 `wait()` 子进程，而子进程则通过 `exec()` 加载并执行命令。例如，当用户输入 `echo hello` 时，shell 的 `runcmd()` 函数会调用 `exec()`。如果 `exec()` 成功，子进程会执行 `echo` 而不是 `runcmd`；当 `echo` 最终调用 `exit()` 时，父进程的 `wait()` 就会返回。

---

### `fork()` 与 `exec()` 分离的哲学

为什么不将 `fork()` 和 `exec()` 合并为一个系统调用？

这是一种重要的**设计哲学**：在 `fork()` 和 `exec()` 之间，可以插入其他操作，例如 **I/O 重定向**。这种分离让 shell 能够在子进程中调整其 I/O 设置（例如关闭标准输入并打开一个文件），然后才 `exec()` 新程序，而不会影响主 shell 自身的 I/O 配置。如果它们是组合的调用，实现 I/O 重定向将会非常笨拙。

xv6 会**隐式地分配大部分用户空间内存**：`fork()` 为子进程分配父进程内存的副本所需的空间；`exec()` 分配足以容纳可执行文件的内存。如果运行时程序需要更多内存（例如通过 `malloc()`），它可以调用 `sbrk(n)` 来增加其数据内存 `n` 个字节，`sbrk()` 会返回新内存的起始地址。

## 2. I/O 与文件描述符

**文件描述符**是一个小整数，代表由内核管理的可读写对象。进程可以通过打开文件、目录、设备、创建管道或复制现有描述符来获得文件描述符。为简化概念，我们通常将文件描述符指向的对象统称为“文件”，因为文件描述符接口将文件、管道和设备抽象化，使它们都表现为**字节流**。

在 xv6 内部，文件描述符是每个进程私有表中的索引，每个进程都有一个从零开始的文件描述符空间。根据约定：
- 文件描述符 **0** 用于**标准输入**。
- 文件描述符 **1** 用于**标准输出**。
- 文件描述符 **2** 用于**标准错误输出**。

shell 利用这一约定来实现 I/O 重定向和管道。shell 总是确保有三个打开的文件描述符（通常默认指向控制台）。

### `read()` 与 `write()`：字节流操作

`read(fd, buf, n)` 系统调用从文件描述符 `fd` 读取最多 `n` 个字节，将其复制到 `buf`，并返回实际读取的字节数。每个文件描述符都有一个关联的**文件偏移量**；`read()` 从当前偏移量开始读取，然后将偏移量推进所读取的字节数。当没有更多字节可读时，`read()` 返回 `0` 表示文件结束（EOF）。

`write(fd, buf, n)` 系统调用将 `buf` 中的 `n` 个字节写入文件描述符 `fd`，并返回写入的字节数。只有在发生错误时，写入的字节数才可能小于 `n`。与 `read()` 类似，`write()` 也在当前文件偏移量处写入数据，并推进偏移量。

以下是 `cat` 程序的简化仿写，它将数据从标准输入复制到标准输出，并在错误时写入标准错误：

```c
#include "kernel/types.h"
#include "kernel/stat.h"
#include "user/user.h"

char buf[512];

void cat(int fd) {
    int n;
    while ((n = read(fd, buf, sizeof buf)) > 0) {
        if (write(1, buf, n) != n) {
            fprintf(2, "lsc : write error\n");
            exit(1);
        }
    }

    if (n < 0) {
        fprintf(2, "lsc: read error\n");
        exit(1);
    }
}

int main(int argc, char *argv[]) {
    int fd, i;
    if (argc <= 1) { // 如果没有参数，从标准输入读取
        cat(0);
        exit(0);
    }

    for (i = 1; i < argc; i++) { // 否则，打开并处理每个文件
        if ((fd = open(argv[i], 0)) < 0) {
            fprintf(2, "lsc: cannot open %s\n", argv[i]);
            exit(1);
        }
        cat(fd);
        close(fd); // 处理完文件后关闭描述符
    }

    exit(0);
}
```

从上述代码可以看出**文件描述符的实用性**：用户无需关心描述符对应的是 I/O 设备、文件还是其他，它们都统一为字节流进行操作。

### `close()`：释放文件描述符

`close()` 系统调用**释放**一个文件描述符，使其可被后续的 `open()`、`pipe()` 或 `dup()` 系统调用重用。新分配的文件描述符总是当前进程中**编号最小的未使用描述符**。

文件描述符与 `fork()` 的结合，极大地简化了 I/O 重定向的实现。`fork()` 会复制父进程的文件描述符表，因此子进程一开始拥有与父进程完全相同的打开文件。而 `exec()` 尽管替换了进程的内存，却**保留了其文件描述符表**。这种行为使得 shell 可以通过以下方式实现 I/O 重定向：

1. 在子进程中**关闭**某个文件描述符（例如标准输入 `0`）。
2. **重新打开**所需的文件，由于“最小可用原则”，新文件会分配到被关闭的描述符（例如 `0`）。
3. 然后调用 `exec()` 运行新程序。

下面是 shell 运行命令 `cat < input.txt` 的简化代码：

```c
char* argv[2];
argv[0] = "cat";
argv[1] = 0;
if (fork() == 0) { // 子进程
    close(0); // 关闭标准输入
    open("input.txt", O_RDONLY); // 重新打开 input.txt，它将获得文件描述符 0
    exec("cat", argv); // 执行 cat，其标准输入现在是 input.txt
}
```

父进程的文件描述符不会被这一系列操作改变，因为它只修改了子进程的描述符。这再次强调了 `fork()` 和 `exec()` 分离的优势：它为子进程提供了在执行新程序前进行 I/O 重定向的机会，而不会影响主 shell 进程。

### `dup()`：复制文件描述符

`dup()` 系统调用用于**复制**一个现有的文件描述符，返回一个指向**同一底层 I/O 对象**的新文件描述符。这两个描述符会**共享同一个文件偏移量**，就像 `fork()` 复制的文件描述符一样。

这是一个使用 `dup()` 将 "hello world" 写入文件的方法：

```c
fd = dup(1); // 复制标准输出（文件描述符 1），新描述符 fd 也指向控制台
write(1, "hello ", 6); // 写入标准输出
write(fd, "world\n", 6); // 通过 fd 写入，同样写入标准输出
```

**注意：** 只有当两个文件描述符通过一系列 `fork()` 和 `dup()` 调用从**同一个原始文件描述符**派生时，它们才共享偏移量。否则，即使它们都打开了同一个文件，也不会共享偏移量。

`dup()` 允许 shell 实现更复杂的重定向，例如 `ls existing-file non-existing-file > tmp1 2>&1`。其中 `2>&1` 告诉 shell 将文件描述符 `2`（标准错误）设置为文件描述符 `1`（标准输出）的副本。这样，所有正常输出和错误信息都将重定向到 `tmp1` 文件中。虽然 xv6 shell 不直接支持错误文件描述符的 I/O 重定向，但有了 `dup()`，实现它并非难事。

文件描述符是一个强大的抽象，因为它**隐藏了底层连接的细节**：一个进程向文件描述符 `1` 写入，可能最终写入到普通文件、设备（如控制台），或者管道。

## 3. 管道 (`pipe()`)

**管道**是一种进程间通信（IPC）机制，它表现为一对文件描述符：一个用于**读取**，一个用于**写入**。数据写入管道的一端后，就可以从另一端读取。管道为进程提供了一种高效的通信方式。

下面的示例代码展示了如何使用管道将数据传递给 `wc` 程序：

```c
int main() {
    char *argv[2];
    argv[0] = "wc";
    argv[1] = 0;
    int p[2]; // p[0] 用于读取，p[1] 用于写入

    pipe(p); // 创建管道

    if (fork() == 0) { // 子进程：作为管道的读取端
        close(0);      // 关闭标准输入
        dup(p[0]);     // 将管道的读取端（p[0]）复制到文件描述符 0（标准输入）
        close(p[0]);   // 关闭原始的 p[0]
        close(p[1]);   // 关闭管道的写入端（子进程不需要写入）
        exec("/wc", argv); // 执行 wc 程序，其标准输入现在是管道
    } else { // 父进程：作为管道的写入端
        close(p[0]);   // 关闭管道的读取端（父进程不需要读取）
        write(p[1], "hello world\n", 12); // 写入数据到管道
        close(p[1]);   // 关闭管道的写入端
        wait(0);       // 等待子进程完成
    }
    exit(0);
}
```

程序首先调用 `pipe()` 来创建一个管道，并在数组 `p` 中存储其读写文件描述符 (`p[0]` 为读端，`p[1]` 为写端)。`fork()` 后，父子进程都拥有指向管道的文件描述符。

- **子进程**：关闭其标准输入 (`0`)，然后使用 `dup(p[0])` 将管道的读取端连接到标准输入。接着关闭原始的管道描述符 `p[0]` 和 `p[1]`（子进程不需要写入），最后 `exec()` 运行 `wc`。这样，`wc` 从其标准输入读取时，实际上就是从管道读取。
- **父进程**：关闭管道的读取端 (`p[0]`)，然后向管道写入数据，最后关闭写入端 (`p[1]`) 并 `wait()` 子进程完成。

**关键的 EOF 信号与文件描述符关闭：**

如果管道中没有可用数据，对管道的 `read()` 操作会阻塞，直到新数据被写入，或者**所有指向管道写入端的文件描述符都被关闭**。在后一种情况下，`read()` 将返回 `0`，表示到达文件末尾（EOF）。

**这就是为什么子进程在执行 `wc` 之前，关闭管道的写入端 (`p[1]`) 如此重要：** 如果 `wc` （或任何读取数据的程序）仍然持有管道的写入端文件描述符，它将永远无法收到 EOF 信号，并会持续等待数据，导致程序无限阻塞。程序只有在管道的**所有写入端**都被关闭时，才能收到 EOF。

xv6 shell 以类似上述代码的方式实现了 `grep fork sh.c | wc -l` 这样的管道命令，其核心逻辑位于 `user/sh.c:100`：

```c
case PIPE:
    pcmd = (struct pipecmd *)cmd;  // 将通用 cmd 类型转换为 pipecmd 类型，包含 left 和 right 子命令
    if (pipe(p) < 0)               // 创建管道，p[0] 为读端，p[1] 为写端
        panic("pipe");
    if (fork1() == 0) {            // 第一个子进程：处理管道左边的命令
        close(1);                  // 关闭标准输出
        dup(p[1]);                 // 将管道写端复制到标准输出
        close(p[0]);               // 关闭管道读端（此子进程不读）
        close(p[1]);               // 关闭原始管道写端（已复制）
        runcmd(pcmd->left);        // 执行左边命令，其输出进入管道
    }
    if (fork1() == 0) {            // 第二个子进程：处理管道右边的命令
        close(0);                  // 关闭标准输入
        dup(p[0]);                 // 将管道读端复制到标准输入
        close(p[0]);               // 关闭原始管道读端（已复制）
        close(p[1]);               // 关闭管道写端（此子进程不写）
        runcmd(pcmd->right);       // 执行右边命令，其输入来自管道
    }
    close(p[0]);                   // 父进程关闭所有管道描述符
    close(p[1]);
    wait(0);                       // 父进程等待第一个子进程
    wait(0);                       // 父进程等待第二个子进程
    break;
```

### 为什么 xv6 为管道两端都 `fork()`？

原则上，可以让管道的左端命令在父进程（即 shell 本身）中运行，但这样做会使实现变得**异常复杂**。

考虑一个假设修改：将 `sh.c` 改为不对 `p->left` 进行 `fork()`，而是在**当前进程（父进程）**中直接运行 `runcmd(p->left)`。

- **问题示例：`echo hi | wc`**
    - 当 `echo hi` 在当前进程中执行并退出时，这个**当前进程会随之退出**。
    - 结果是，负责 `fork()` 并运行管道右端命令 (`wc`) 的代码将**永远没有机会执行**。`wc` 将无法启动，整个管道操作将不会产生输出。

- **尝试修复与引入的复杂性：**
    - 你可以尝试修改 `runcmd`，让它在作为“内部进程”执行时不要调用 `exit()`。
    - 然而，这会**极大地增加代码的复杂性**：`runcmd` 需要知道它是否处于一个“内部”上下文中，从而影响其通用性。
    - 类似的复杂性也会出现在不对 `p->right` 执行 `fork()` 的情况下。

- **另一个问题示例：`sleep 10 | echo hi`**
    - 如果 `echo hi` 在没有 `fork()` 的情况下立即运行，它将**立即打印 "hi"** 并退出，而不会等待 `sleep 10` 完成。这完全违背了管道的语义（右侧命令通常依赖左侧的输出或完成）。

**xv6 的选择：简单性优先**

为了保持 `sh.c` 代码的**尽可能简单**，xv6 不会试图避免创建“内部进程”（即直接在 shell 进程中运行管道命令）。它始终为管道的**每一端都 `fork()` 一个独立的子进程**。

这种设计确保了：
- **隔离性**：每个命令都在一个**干净、隔离的环境**中运行。
- **通用性**：`runcmd` 始终可以假设它在一个独立的进程中，执行完毕后可以**安全地退出**，而无需担心破坏 shell 的整体逻辑。

这种设计虽然可能牺牲了一点点进程创建的开销，但换来了代码的巨大**简化和健壮性**。

### 管道相较于临时文件的优势

使用管道而非临时文件进行进程间通信，至少有四个显著优势：

1. **自动清理**：管道在不再使用时会自动清理。相比之下，使用临时文件进行重定向时，shell 必须小心地在用完文件后删除它们。
2. **数据流大小**：管道可以传输**任意大小**的数据流，不受磁盘空间的限制。而文件重定向则需要磁盘上有足够的空闲空间来存储所有数据。
3. **并行执行**：管道允许管道阶段**并行执行**。第一个程序可以开始生成输出，而第二个程序同时开始处理输入，无需等待第一个程序完全完成。文件方法则要求第一个程序在第二个程序启动之前完全完成。
4. **高效的进程间通信**：管道的**阻塞式读写语义**（即读取端在无数据时会等待，写入端在缓冲区满时会等待）比文件的非阻塞语义更高效，更适合进程间的实时通信。

## 4. 文件系统

xv6 文件系统提供了两种主要对象：

- **数据文件**：包含未解释的字节数组。
- **目录**：包含对数据文件和其他目录的命名引用。

这些目录形成一个树状结构，从一个特殊的**根目录 (`/`)** 开始。

- **绝对路径**：像 `/a/b/c` 这样的路径指的是从根目录 `/` 开始，依次进入名为 `a` 的目录、名为 `b` 的目录，最终指向 `c` 文件或目录。
- **相对路径**：不以 `/` 开头的路径是相对于**当前工作目录**进行解析的。当前工作目录可以通过 `chdir()` 系统调用进行更改。

例如，以下两个代码片段打开的是同一个文件（假设相关目录都存在）：

```c
chdir("/a");           // 改变当前工作目录到 /a
chdir("b");            // 改变当前工作目录到 /a/b
open("c", O_RDONLY);   // 相对于当前目录打开 c，即 /a/b/c
```

与此相对：

```c
open("/a/b/c", O_RDONLY); // 直接使用绝对路径打开文件，不改变也不依赖当前工作目录
```

### 创建文件与目录

xv6 提供以下系统调用来创建新的文件和目录：

- **`mkdir(path)`**：创建一个新目录。
- **`open(path, O_CREATE | O_WRONLY)`**：使用 `O_CREATE` 标志打开一个文件时，如果文件不存在则会创建一个新的数据文件。
- **`mknod(path, major, minor)`**：创建一个新的**设备文件**。

示例：

```c
mkdir("/dir");              // 创建目录 /dir
fd = open("/dir/file", O_CREATE | O_WRONLY); // 创建并打开 /dir/file
close(fd);
mknod("/console", 1, 1);    // 创建设备文件 /console，主设备号 1，次设备号 1
```

`mknod()` 创建的设备文件与**主设备号**和**次设备号**（`mknod()` 的两个参数）相关联，它们唯一标识一个内核设备。当进程稍后打开设备文件时，内核将根据这些设备号调用相应的内核设备驱动来实现 `read()` 和 `write()` 系统调用，而不是使用文件系统来处理数据。

一个文件的**名称**和**文件本身**是不同的。同一个底层文件（在 xv6 中称为 **inode，索引节点**）可以有多个名称（称为 **link，链接**）。每个链接都是目录中的一个条目，包含一个文件名和一个对相应 inode 的引用。Inode 存储了文件的**元数据**（用于解释或帮助理解文件信息的数据），包括其类型（文件/目录/设备）、大小、文件内容在磁盘上的位置以及指向该文件的链接数量。
